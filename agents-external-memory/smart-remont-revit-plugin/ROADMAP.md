# Roadmap и обсуждённые направления

Документ фиксирует идеи из обсуждений **без обязательства реализации**. Актуальное «как сейчас» — в остальных файлах этой папки.

---

## 1. SPECIFICATION_CODE на ведомостях

**Проблема:** хардкод `ScheduleNamesExact` ломается при переименовании ведомости.

**Идея:** общий параметр на Views (`ViewSchedule`), значения = `param_code` или отдельный код.

**В коде:** поиск ведомости по `LookupParameter("SPECIFICATION_CODE")`, fallback на имена.

**Не решает:** смену группировки/колонок внутри ведомости.

---

## 2. Независимость от логики ведомости

**Требование заказчика:** если кто-то меняет настройки ведомости, плагин не должен ломаться.

**Вывод:**

- Парсинг `ViewSchedule` **всегда** зависит от структуры таблицы.
- Полная независимость → источник **параметры на Room/элементах**, ведомость только для отображения.
- Компромисс: вынести маппинг колонок в JSON (всё равно нужен при смене **режима** таблицы).

---

## 3. Сверка: ведомости vs модель (рекомендованный следующий шаг)

**Идея:** оставить отправку `MEASURES` из ведомостей; параллельно считать probe из модели и показывать Δ в UI.

| Этап | Содержание |
|------|------------|
| 0 | Интерфейс `Compare(snapshot, modelProbe)` + колонки в `RoomMeasurementsWindow` |
| 1 | Probe для «простых» метрик (двери, плитка по полам) |
| 2 | Допуски ±% / ±0.05 м; статус «сверка недоступна» |
| 3 | Не отправлять probe на backend (только UI), опционально позже |

**Не ожидать совпадения** для `WALL_AREA_MINUS` (брутто в модели vs нетто в ведомости).

Файлы: новый `RoomMeasurementsModelProbe.cs`, расширение `RoomMeasurementsModels`, UI в `RoomMeasurementsWindow`.
