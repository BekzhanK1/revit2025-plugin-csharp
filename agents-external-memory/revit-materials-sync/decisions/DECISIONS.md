# Решения — revit-materials-sync

| # | Решение | Почему |
|---|---------|--------|
| 1 | Термин "по договору" в презентации → заменить на "из ТК" / "из текстового конструктора" | Материалы ремонта хранятся в `client_material_tab` (ТК), договор (`client_request_tab`) — только точка входа по `client_request_id` |
| 2 | `client_request_material_tab` не существует — реальная таблица `client_material_tab` | Проверено по `information_schema.columns` на dev |
| 3 | Не добавлять поле `revit_category` в `material_tab` | Категория Revit уже зашита внутри `.rfa`-семейства, Revit получает её при `LoadFamily()` без внешней подсказки |
| 4 | 4 новых поля вместо большего числа: `revit_file_type`, `revit_file_url`, `revit_file_hash`, `revit_asset_name` | Минимум для флоу: тип → url → hash (кэш) → имя ассета. Масштабируется, если `.rfa` — это семейства-типы (~15–20), а не файл на каждую номенклатуру (~5 287) |
| 5 | Не переиспользовать/не менять `client_material/tk/read/` — сделать новый эндпоинт `/revit/material/read/` | Существующий используется UI ТК (обёртка grant-блоков в варианте по `client_request_id`, другой контракт); плагину нужен свой узкий контракт с дедупом по `material_id` и только Revit-релевантные материалы |
| 6 | Дедуп по `material_id` в новой SP (`DISTINCT ON`) | Один материал может встречаться в нескольких комнатах ТК — плагину нужно скачать файл один раз, а не N раз |
| 7 | Классификация `surface` / `rfa` / `none` — по `material_type_tab.material_type_code`, не по `material_type_id` напрямую | `material_type_id` может отличаться между окружениями/новыми типами; код (`TILE`, `PAINT`...) стабильнее |
| 8 | Пока без MinIO — `revit_file_url`/`revit_file_hash` заполняются фиктивными, но стабильными значениями (`md5(url)`) | Не блокировать разработку endpoint/плагина ожиданием реального хранилища; контракт API не изменится при переходе на MinIO — поменяется только источник значений |
| 9 | Заполнение фиктивных ссылок (task-04) — только по явному запросу пользователя перед выполнением на реальной БД | Правило `no-autonomous-database-writes` — UPDATE на dev/prod без явного подтверждения не выполняется |
| 10 | Backend Revit materials — отдельный пакет `revit/`, не в `INSTALLED_APPS`, только `office_api/urls.py` → `/revit/` | Не смешивать с `common/`; `revit_events` остаётся в `common/revit_events/` (legacy) |
| 11 | `revit_file_url` на реальных данных (2026-07-01, `remont_id=21838`) — **подписанный (presigned) MinIO URL с TTL ~12ч** (`X-Amz-Expires=43199`, `X-Amz-Signature`), не стабильная ссылка. `revit_file_hash` пока везде `NULL` | Кэш в плагине **нельзя** ключевать по URL/`md5(url)` — URL меняется при каждом запросе к API. Ключ кэша на стороне плагина (task-06) — `material_id` (+ опционально `revit_file_type`), сравнение по `revit_file_hash`, когда backend начнёт его реально заполнять (сейчас `NULL` → пока считаем «неизвестно, всегда докачивать при отсутствии локальной копии по `material_id`») |
| 12 | Импорт в проект (task-07) — сначала только `revit_file_type = 'rfa'` через `Document.LoadFamily()`, без автоматической расстановки экземпляров в модели | `surface`-материалы (текстуры/`.rvt`-библиотека материалов) требуют другого механизма импорта (`Application.OpenSharedFile` / перенос материалов между документами) — отдельная будущая таска (task-08+), не блокировать MVP скачивания/загрузки семейств |
