# ДС «Изменение ТК» и наборы: как работает и где ломается

Разбор от 2026-10-06. Данные — `dev_prod_smartremont` (только чтение): заявка 3071538, ДС 46989, подборы 334 и 398. Код — плагин (`dev1.0.1`), `myspace-backend` (ветка `dev`), `myspace-frontend` (ветка `dev`). Плагин ещё не запущен в работу: всё, что ниже про плагин, — проверка кода, а не подтверждённое поведение.

## Коротко

1. **Объёмы берутся из ведомостей по ID материала.** Источник — колонка «ID материала», запасной вариант — «Наименование» вида `12114_Розетка ...`. Сумма считается по паре (комната, material_id). Отправляются только изменения, `material_cnt` и `set_items` по каждому `client_material_id`.
2. **При инициализации `.rfa` элементов набора не скачиваются.** Функция плагина берёт только голову набора. Страница `/revit-preset-materials` показывает и состав набора, поэтому загруженные туда `.rfa` розеток и рамок до проекта не дойдут.
3. **Уменьшение до нуля не отправляется.** Если позиции из ТК нет в ведомости комнаты, плагин считает это нормой и ничего не шлёт.
4. **Без привязанной ДС плагин не видит состав набора.** `tk/read` отдаёт состав строкой HTML, а не `items_json`.

## Как устроен набор (на примере 5549 «Выключатели и розетки AUROOM»)

| Уровень | Таблица | Пример |
|---|---|---|
| Голова набора | `material_set_tab.material_id`, в ТК — `client_material_tab.material_id` + `material_cnt` | 12102 «Выключатель 1-клавишный», `revit_file_type = rfa` |
| Состав набора (справочник) | `material_set_item_tab` | 19 позиций: механизмы 12104–12122, заглушка 12129, HDMI 12131, рамки 12133–12141, STEKKER 12499–12505 |
| Состав в ТК заявки | `client_material_set_item_tab` (по `client_material_id`) | Гостиная: 12114 ×7, 12122 ×1, 12129 ×1, 12131 ×0.5, рамки 12133 ×5 / 12135 ×1 / 12137 ×1 |
| В подборе | `preset_material_tab.material_id` = голова (12102), `material_set_id` = 5549 | подбор 398, конструктив «Электрика» |

Одна строка ТК «Электрика» на комнату — это голова плюс 19 элементов. Голова — тоже материал со своим количеством: в Балконе и Прихожей 1, в остальных комнатах 0.

На `dev_prod` у всех 19 элементов набора 5549 `revit_file_type = none` и нет `revit_file_url`. Ни в подборе 334, ни в 398 нет элемента набора с `.rfa`. Если на `/revit-preset-materials` `.rfa` уже загружены, то это сделано на боевой базе после копии `dev_prod`; проверить это мне не дали права.

## Процесс по шагам

### 1. Инициализация: какие `.rfa` скачиваются

| Что | Функция | Источники material_id |
|---|---|---|
| Страница `/revit-preset-materials` | `read_revit_materials_by_preset_kit` | (1) `preset_material.material_id`, (2) голова `material_set_tab.material_id`, (3) **состав `material_set_item_tab`** |
| Плагин, `GET /revit/plugin/material/read/` | `read_revit_material_by_client_request` | (1) `preset_material.material_id` подбора заявки, (2) `client_material_tab.material_id` из ТК. **Состава набора нет** |

На данных: для подбора 334 страница отдаёт 66 материалов, а плагин для заявки 3071538 — 38. Недостающие 31 — элементы наборов (на `dev_prod` все с типом `none`).

**Подтверждено на `dev_prod`:** заявка 2535356 (подбор 343). Унитаз 12573 (`rfa`, файл загружен) лежит внутри набора 11453 с головой 18579, количество 1. `read_revit_material_by_client_request(2535356)` его не возвращает, значит при init `.rfa` унитаза не скачается. В заявке 3196204 зеркало 15777 из набора 8954 приходит, но только потому, что подбор 341 содержит зеркало ещё и отдельной позицией.

**Вывод:** элементы набора, у которых на странице загружен `.rfa`, при инициализации не скачаются. Синхронизация материалов отчитается об успехе, потому что не знает о них. Семейства розеток и рамок с `SR_ID` = 12114 и т.п. окажутся в проекте, только если они уже есть в шаблоне `.rte`.

**Исправление (SQL):** в `read_revit_material_by_client_request` добавить два источника:
- `material_set_item_tab` для наборов подбора (как источник 3 на странице);
- `client_material_set_item_tab` для наборов ТК заявки, если клиент поменял состав.

`DISTINCT ON (material_id)` уже стоит, дублей не будет.

### 2. Как плагин читает объёмы электрики

`TkQtyScheduleService` с конфигом `%APPDATA%\SmartRemont\RevitPlugin\tk_qty_schedule_mappings.json`, источник `ELECTRICS`:

- Ведомость «Спецификация электрических приборов..», «.» или без точки — первое найденное точное имя.
- Режим `GroupedByRoomHeader`: строка без ID и без количества задаёт текущую комнату, следующие строки относятся к ней. Колонка «Помещение» / «Помещения» / «Комната», если есть, имеет приоритет.
- ID: колонка «ID материала» — целое число без букв перед ним. Если колонки нет или ячейка пустая, ID берётся из «Наименования» / «Описания» по шаблону `^(\d+)_(.+)$` (`12114_Розетка ...`). Формат `ID_12114` не распознаётся.
- Количество: «Кол-во, шт.», «Кол-во, шт», «Число, шт», «Кол-во». Если колонки нет, считается 1 на строку.
- Строки «Итого» и «Общий итог» пропускаются. Сумма — по (комната, material_id).

### 3. Сверка с ТК/ДС (`DsTkChangeWindow` → `DsTkCompareService`)

1. ТК: `GET /revit/plugin/tk/read/` → SQL `read_client_material`. Состав набора приходит только полем `set_materials` — HTML-строкой `id / название / кол-во ед<div class="hr hr6"></div>...`. `items_json` там нет, и плагин его не находит (`ParseSetItems` ищет `items_json` / `items` / `set_items`).
2. Если привязана ДС: `GET /client_request/{id}/ds/{ds}/tk_material/` → `tk_ds_client_material_read`. Здесь `items_json` есть с полным составом (проверено на ДС 46989). Плагин подменяет данными ДС объёмы и состав (`ApplyDsQtyOverlay`), затем разворачивает наборы (`FlattenSets`): голова и каждый элемент становятся отдельными строками с одним `client_material_id`.
3. Сравнение по (комната, material_id):

| ТК/ДС | Ведомость | Статус | Отправится |
|---|---|---|---|
| есть | есть, объём совпадает (±0.05 или ±1%) | `qty_match` | нет |
| есть, ввод разрешён | есть, объём другой | `qty_mismatch` | **да** |
| есть, ввода нет | есть, расхождение ≥10% / меньше | `qty_project_alert` / `qty_soft_diff` | нет |
| есть | **нет строки** | `qty_tk_only` | **нет** |
| нет | есть | `qty_schedule_only` | нет |

### 4. Отправка (`POST /revit/plugin/ds/tk-change/apply/`)

`BuildApplyItems` группирует кандидатов по `client_material_id`:

```json
{
  "client_request_id": 3071538,
  "ds_id": 46989,
  "items": [{
    "client_material_id": 344311121,
    "material_cnt": null,
    "expected_material_cnt": null,
    "unit": null,
    "set_items": [
      {"material_id": 12114, "material_cnt": 5, "expected_material_cnt": 7, "unit": "шт"}
    ]
  }]
}
```

Бэкенд (`revit_ds_tk_apply_services.py`): если `material_cnt` головы `null`, он берётся из текущей ДС. Неотправленные элементы набора тоже берутся из ДС, а не обнуляются. Каждый элемент сверяется с `expected_material_cnt` (защита от гонок) и по единице (`шт.` и `шт` после нормализации равны). Затем по всем позициям выполняется `tk_change_set_item_cnt` в одной транзакции с перечиткой. Эта часть выглядит корректно.

## Двери и формулы: что не рисуется в Revit

В Revit рисуют дверное полотно, а ручки, замки, петли и погонаж коробки — нет. Ниже, как это устроено в данных (заявка 3071538, `dev_prod`).

| Строка ТК | Набор | Голова | Формула головы | Элементы набора (формула) | Ввод объёма в MySpace |
|---|---|---|---|---|---|
| Межкомнатная дверь | 10564 / 10565 | полотно 17726 / 17727 | `DOOR_CNT × 1` | стойка 17731 (`2.55`), добор 17732 (`2.5`), наличник 17733 (`5`) | да |
| Фурнитура | 10953 / 10954 | ручка 18467 | `DOOR_CNT × 1` | замок 18469 (`1`), завертка 18470 (`1`) | да |
| Навесы | 10952 | петля 18468 | `DOOR_CNT × 3` | — | **нет** |

Как считаются формулы:

- `DOOR_CNT` — это код замера «Межкомнатные двери» помещения (тот же, что плагин отправляет в `measures/apply` из «Спецификации дверей»).
- Формулы вычисляет только SQL `fill_client_material_cnt`: «кол-во материала ... исходя из внесённых замеров». Его вызывают `constrcutor_fill_material_cnt` (сборка ТК), `ds_room_change_process` и `room_change_accept` (ДС площади), `ddu__create_request_v2`, `get_client_request_marketplace_price`.
- **В ДС «Изменение ТК» формулы не работают.** `tk_change_set_item_cnt` пишет ровно те числа, что пришли. Фронт MySpace (`buildTkSetItemSaveArrays`) тоже отправляет только то, что менеджер ввёл руками в голову и в каждый элемент набора.
- Формулы элементов набора — **константы на комнату, а не «× количество дверей»**. В гостиной `DOOR_CNT = 0`, полотно 0, а стойка 2.55, добор 2.5, наличник 5, замок 1 стоят уже в договорном ТК. Похоже на ошибку в справочнике наборов: элементы должны зависеть от числа дверей.

Что сделает плагин, если в ванной в модели стало 2 двери вместо 1:

1. Из «Спецификации дверей» (`DOORS`, колонка «ID материала» = 17726) получится полотно = 2, ТК = 1 → `qty_mismatch` → в ДС уйдёт полотно 2.
2. Ручки, замка и завертки в модели нет → `qty_tk_only` → не отправляются, остаются 1.
3. Стойка, добор и наличник (элементы набора двери) — тоже нет в ведомости → остаются 2.55 / 2.5 / 5.
4. Петли: строки нет, и ввод в MySpace запрещён → остаются 3.

Итог: ДС получится несогласованной — 2 полотна, 1 ручка, 3 петли, погонаж на одну дверь.

Варианты решения (нужно решение бизнеса):

- **A. Пересчёт зависимых позиций в плагине.** Для наборов с формулой головы `DOOR_CNT` и т.п. взять количество дверей комнаты из ведомости и посчитать `голова = кол-во × consumption`, элементы — по формуле. Отправлять вместе с полотном. Петли упираются в запрет ввода: нужен либо флаг на конструктиве, либо особое правило на backend.
- **B. Пересчёт на backend.** В `apply_ds_tk_qty_from_revit` после записи головы с формулой `DOOR_CNT` пересчитать все позиции комнаты с той же формулой (как `fill_client_material_cnt`, но в рамках ДС). Логика будет в одном месте и одинаковой для плагина и MySpace.
- **C. Отправлять замер, а не объёмы.** Плагин уже шлёт `DOOR_CNT` в замеры. Если ДС ТК может пересчитываться от замеров (как ДС площади через `ds_room_change_process` → `fill_client_material_cnt`), то двери вообще не надо слать объёмами.

## Предложение: считать объёмы на backend по формулам ТК

### Почему

Весь ТК — это формулы от замеров помещения:

- `client_material_tab.formula_material` × `consumption_material` для головы;
- `client_material_set_item_tab.formula` × `consumption` для элементов набора.

Формулы бывают трёх видов: константа (`1`, `0.5`, `8`), один код замера (`DOOR_CNT`, `FLOOR_AREA`, `SOCKET_MAIN`, `FRAME_SINGLE`, `SWITCH_SINGLE`...) или выражение (`3*DOOR_CNT`, `EXTERNAL_SW_DOUBLE+EXT_DOUBLE_PEREK_SW`). Электрика — тоже формулы: у каждого элемента набора 5549 свой код замера (`param_tab`: `SOCKET_MAIN` — «Розетка обычная», `FRAME_SINGLE` — «Рамка однопостная»...).

Считает их `fill_client_material_cnt` → `get_formula_result_general` → `get_formula_result` (подстановка `param_code` через `replace` + `_calc_expression`). В справочниках ~8.5 тыс. выражений, есть пробелы и запятые вместо точек. Повторять этот движок в C# — гарантированное расхождение с MySpace, поэтому считать должен backend.

### Как должно работать

1. **Плагин собирает замеры комнат из модели**: то, что уже собирает для `measures/apply` (`PERIMETER_FLOOR`, `PERIMETER_ROOF`, `WALL_AREA_MINUS`, `PLITKA_AREA`, `DOOR_CNT`, `APRON_AREA`, `MOLDING_PERIMETER`), плюс `FLOOR_AREA` из помещений.
2. **Электрика — исключение**: количества по `material_id` из «Спецификации электрических приборов» (как сейчас). Если ведомость комнаты найдена, а материала в ней нет — это 0.
3. **`POST /revit/plugin/ds/tk-change/preview/`** `{client_request_id, ds_id, rooms:[{room_id, params:{DOOR_CNT:2, ...}}], electrics:[{room_id, material_id, cnt}]}`. Backend для каждой позиции ДС считает целевой объём:
   - формула с параметрами из запроса → `get_formula_result_by_params(formula, params jsonb)` (новая SQL-функция: та же подстановка + `_calc_expression`, но параметры из jsonb, а не из планировки);
   - параметр, которого нет в запросе, берётся из планировки, то есть остаётся как есть;
   - константы не трогаются (HDMI 0.5, «черновой материал» 1);
   - электрика: элементы и голова набора, у которых формула — один электрический код, получают число из `electrics` (× `consumption`, обычно 1).

   Ответ — список позиций: текущий объём в ДС, договорной, целевой, причина блокировки. В базе ничего не меняется.
4. **Плагин показывает превью** (как сейчас `DsTkQtyApplyPreviewWindow`), но уже с серверными цифрами.
5. **`POST /revit/plugin/ds/tk-change/apply/`** — тот же запрос плюс ожидаемые текущие объёмы из превью. Backend пересчитывает, сверяет ожидания и пишет через `tk_change_set_item_cnt` теми же правилами, что фронт MySpace (`buildTkSetItemSaveArrays`): новое изменение несёт весь состав набора, повторное — только изменившиеся элементы. Всё в одной транзакции.

Протокол записи «как во фронте» уже повторён в `revit_ds_tk_apply_services._build_call` — меняется только источник чисел.

### Что это закрывает

1. **S8**: формулы элементов дверных наборов надо исправить в справочнике (`2.55` → `2.55*DOOR_CNT` и т.п.). Иначе пересчёт оставит их константами.

## Открытые вопросы

1. Где в шаблоне проекта лежат семейства розеток и рамок с `SR_ID` = 12114 и т.п.? Сейчас их может дать только шаблон `.rte`, а не синхронизация материалов (S1).
2. Как в модели проектировщик кладёт выключатель-голову 12102? Как отдельное семейство с `SR_ID` = 12102 или как механизм внутри рамки? От этого зависит, будет ли в ведомости строка 12102.
3. Голова набора в ТК (12102 = 0 в большинстве комнат) — это реальное количество выключателей или служебная строка? На отправку уходит как обычный материал.
4. На prod `.rfa` элементов наборов действительно загружены? На `dev_prod` их нет. Проверка prod была заблокирована правилами авто-режима.
